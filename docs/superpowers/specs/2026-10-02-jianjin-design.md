## 1. 问题

具身智能的训练数据主要靠遥操作采集：采集员操纵主臂，机器人跟着做，录下视频和关节数据。国内为此建了一批数采场。

| 事实 | 来源 |
|---|---|
| 全国至少 15 座大型数采场，单场 3,000 到 5,000 平米；大型数采场投入超过一亿元，基本没有盈利 | 甲子光年，2026-06-26 |
| 北京人形机器人创新中心的基地有 120 多台机器人，数据卖 500 到 1,000 元一小时 | 同上 |
| 同一个动作要重复 700 多遍；过快或多余的动作会让数据作废 | 同上 |
| 一班约 8 小时，实采 6 小时，过三道质检后剩 3 到 4 小时有效 | 北京市政府网 2026-09-04 或腾讯 2026-09-03，出自哪篇待核 |
| 质检和标注主要靠人工；「采了 100 个小时，漏斗筛选下来只有 50 个小时有效」 | 甲子光年；单个受访者的说法，不是行业统计 |

这些数字是调研 agent 从报道里读到的，总管没有逐条复核。写进路演材料之前，先回原文再核一遍。

痛点归结为两条：

1. 坏示范靠人一条条看，慢，而且贵。
2. 作废的原因没有回流给采集员，同样的错下一班还会再犯。

## 2. 用户和卖点

- 买单方：具身智能数采场，以及自建遥操作团队的机器人公司。
- 使用者：质检员和数采场主管；采集员每班收到反馈。
- 一句话：录完的每条示范，拣金自动判成「合格」「存疑」「作废」，作废的写清原因和出问题的时间点。质检员只看存疑的，采集员每班拿到自己的问题清单。

卖点三条：

1. 说得清原因：不只给分数，还指出第几秒出了什么事、属于哪一类失败。
2. 人只看存疑的：人工质检从「每条都看」变成「只看机器拿不准的」。
3. 数据不出场：数采场的数据就是它卖的货。拣金在本地跑，关节体检用笔记本，视频评判用场内显卡，报告是离线的单个网页文件。

## 3. 范围

必做：

1. 读入 LeRobot（v3）和 RoboMIND（HDF5）两种格式，统一成一种示范结构。
2. 关节体检，只用 CPU。
3. 视频评判：Robometer-4B 和 TOPReward 两个适配器。
4. 诊断：合并信号，出判定、原因和时间点。
5. 离线单文件网页报告：每条示范一张体检单，加整批数据的作废漏斗；数据里有采集员编号时，再按人统计问题分布。公开数据没有采集员编号，演示里这一栏会是空的，等试点数据。
6. 评测脚本：三张考卷，见第 6 节。
7. 第 4 周加 Cosmos 3 适配器，给 Nebius 赛道用，见第 7 节。

可做：

- 进度曲线的交互查看。
- 同一任务里不同采集员的对比视图。

不做：

- 实时接入数采场的采集流水线。
- 训练策略来证明筛选有效。
- 任何硬件。
- 云服务（和「数据不出场」冲突）。

## 4. 架构

Python 3.12，uv 管依赖，pytest 测试，和烽燧、虎符一样。

核心只依赖 numpy、h5py、pyarrow 和一个视频解码库，直接读文件格式，不 import LeRobot。视频评判的模型依赖（torch、transformers 等）放进可选的 `judges` 依赖组，没装也能跑关节体检。

### 4.1 模块

| 模块 | 干什么 | 输入 | 输出 |
|---|---|---|---|
| `ingest` | 读 LeRobot v3 和 RoboMIND HDF5 | 数据集路径 | `Episode` 序列 |
| `checks` | 关节体检，每条规则一个纯函数 | `Episode` | `Finding` 列表 |
| `judges` | 视频评判适配器：Robometer、TOPReward、Cosmos 3 | 视频和任务描述 | 每帧进度和成功概率，或文字解释 |
| `diagnose` | 合并信号，出判定 | `Finding` 列表和评判结果 | `Verdict` |
| `report` | 生成离线单文件网页 | `Verdict` 序列 | 一个 HTML 文件 |
| `eval` | 跑三张考卷 | 考卷数据和标签 | 指标表，带分母 |

### 4.2 数据结构

- `Episode`：`id`、`source`、`task`（任务描述）、`fps`、`cameras`（各路视频的读取器）、`state`（关节状态，T×D）、`action`（动作，T×D）、`gripper`（夹爪开合，能识别时才有）、`operator_id`（有才填）、`meta`。
- `Finding`：`check`（哪条规则或哪个模型）、`cause`（失败原因类别，见第 5 节）、`t0` 和 `t1`（秒）、`score`、`evidence`（一句人话）。
- `Verdict`：`label`（合格、存疑、作废）、`causes`（`Finding` 列表）、`not_checked`（没查的项目和原因）、`progress`（进度曲线，跑了视频评判才有）。

实现时的出入（2026-10-02，第一周计划）：`Episode` 加了 `timestamps`、`state_names`、`gripper_index`，`gripper` 改成按 `gripper_index` 从 `state` 取的属性，注入缺陷时夹爪不会和关节错位；`Finding` 加了 `hard`，标记客观硬规则。

### 4.3 判定规则

错杀比漏判贵：一小时数据卖 500 到 1,000 元，误判作废一条就是白扔钱。所以判定偏保守：

- 作废：至少两个彼此独立的信号指向同一处问题，或者一条客观硬规则触发（比如数据截断、关节读数缺失）。「独立」指来源不同：关节规则算一个来源，每个视频模型各算一个来源；「同一处」指两个信号报出的时间区间有重叠。
- 存疑：只有一个信号触发，或者两个视频模型的结论相反。
- 合格：其余情况。
- 缺了某种数据（比如没有夹爪通道），对应的规则记进 `not_checked`，不当成通过。

阈值在考卷 A 的开发集上定，测试集只用来报成绩。

### 4.4 降级和出错

- 没有 GPU，或者没装 `judges` 依赖：只跑关节体检，报告顶部写「没跑视频评判」。
- 某条示范读不了：记进报告的「读取失败」一栏，不中断整批。
- 模型输出按「示范内容哈希加模型版本」缓存成旁路文件，不改原数据；换了模型不会读到旧结果。

### 4.5 命令行

```
jianjin check <数据集路径> --out report.html [--judges robometer,topreward]
jianjin eval <考卷名> [--split dev|test]
```

### 4.6 测试

- 每条关节规则用合成轨迹写单元测试，先写测试再写规则。
- 读入模块用测试里生成的小 HDF5 和 parquet 文件测。
- 视频评判适配器用假模型测接口，真模型只在评测里跑。
- 报告生成用一份固定输入做快照测试。

## 5. 失败原因分类

先用下面七类。拿到 RoboMIND 的失败标签后，按它的分类对齐。

2026-10-02 核：RoboMIND 公开的失败示范把原因写成中文目录名，共 11 类（括号里是条数）：动作不流畅（557）、二次抓取（284）、触碰多余（232）、夹取前碰撞（217）、目标移位（118）、失败放置（113）、轨迹异常（39）、动作不规范（38）、速度过快（36）、机械臂异常（17）、夹爪出境（15），另有 12 条没有原因目录。论文里是另一套 9 类，两套对不上，以公开数据的 11 类为准。原来写的「定位不准占 48%」是论文里 ACT 策略在人形机器人任务上测试时的失败统计，不是遥操作示范的失败，不能这么引。和下表的对应关系在考卷 C 开工时定。

| 类别 | 主要靠什么发现 |
|---|---|
| 没做完 | 视频进度曲线没到头，示范在任务完成前结束 |
| 定位不准 | 接近目标时反复来回修正，视频进度停滞 |
| 夹爪没合上（抓空） | 夹爪闭合后进度不涨，闭合幅度异常 |
| 物体掉落 | 夹爪中途意外张开，或者进度曲线突然回落 |
| 多余动作 | 路径长度远超必要，动作和任务无关 |
| 停顿过长 | 关节速度长时间接近零 |
| 指令不符 | 视频评判认为做的不是任务描述里的事 |
| 数据异常 | 读数缺失、丢帧、示范过短；客观硬规则，一条就能判作废 |

## 6. 验证：三张考卷，都不用机器人

### 考卷 A：注入缺陷（主开发集）

在真机录的成功示范上动手脚，每条的答案已知：

- 截掉结尾，对应「没做完」。
- 插入静止帧，对应「停顿过长」。
- 换掉任务描述，对应「指令不符」。

数据用 LeRobot Hub 上公开的 SO-101 示范（只选授权写明的），拿得到 RoboMIND 就加上它的成功示范。

指标：每类缺陷的检出率和误报率（按示范计）；报出的时间点是否落在注入的区间里。按任务切开发集和测试集，不按示范随机切。

报告里写明：这是在真数据上造出来的假失败。

#### 第一批结果（2026-10-02，只用关节数据，没跑视频评判）

这是在真机成功示范上人工造的失败，不是真实失败。开发集定阈值，测试集只跑了一次。区间是 95% Wilson 区间。随机种子 0。

| 切分 | 数据 | 缺陷 | 检出 | 时间点落在注入区间 | 原样示范上也报了这一类 |
|---|---|---|---|---|---|
| 开发 | SO-100 放方块 50 条、叠方块 56 条（注入用 103 条，3 条短于 3 秒没注入） | 截掉结尾 → 没做完 | 99/103 = 96%（90% 到 98%） | 99/103 | 2/106 = 2%（1% 到 7%） |
| 开发 | 同上 | 插入静止帧 → 停顿过长 | 101/103 = 98%（93% 到 99%） | 101/103 | 0/106 |
| 测试 | SO-100 分拣 52 条、SO-101 乐高块 50 条、SO-101 双臂叠毛巾 100 条（注入用 201 条） | 截掉结尾 → 没做完 | 198/201 = 99%（96% 到 99%） | 198/201 | 11/202 = 5%（3% 到 9%） |
| 测试 | 同上 | 插入静止帧 → 停顿过长 | 199/201 = 99%（96% 到 100%） | 199/201 | 0/202 |

- 测试集上原样示范被报「没做完」的 11 条，全在双臂叠毛巾，全由手腕转动关节触发；两个单臂数据集是 0/102。叠完毛巾时手腕转到哪个角度本来不固定。要修得另找一个双臂开发集，不能拿测试集调。
- 阈值（开发集选出）：`still_rate=0.02`、`pause_s=3.0`、`end_pose_max=0.3`。规则是原样报出不超过 5% 的前提下定位对的最多。明细在 `results/exam_a_dev.json`、`results/exam_a_test.json`。
- 顺带抓到的真问题：`lerobot/svla_so100_stacking` 里有 3 条示范只有 1 帧、14 帧、28 帧（ep 20、37、38），被「示范过短」硬规则判出。
- 否决的方案：「录到最后手臂还在动就算没做完」。开发集上不管阈值怎么取，原样示范被误报的比例都在 21% 到 87% 之间，因为这些公开数据录到最后手臂常常还在动。换成「最后一帧的姿态和同任务中位收尾姿态比」。
- 局限：考卷 A 的检出率高，是因为注入的缺陷在关节上很干净（截断后停在半路、静止帧完全不动）。真实失败不会这么干净，要看考卷 B 和 C。

### 考卷 B：RoboVAD

- 内容：机械臂操作视频，逐帧标注有没有异常；数据和代码公开在 Zenodo，CC BY-SA 4.0。
- 做法：按论文的评测协议，零样本（不在 RoboVAD 上训练），报帧级 micro AUC，和论文里的方法并列。
- 参照：论文说在最难的设置下，所有方法都不到 70%。
- 2026-10-02 核（论文 arXiv 2609.17843、Zenodo records/22754659，读了 zip 目录没整包下载）：
  - 1,078 条，正常 616、异常 462，5.75 小时，异常事件 1,570 个；机械臂是 SO-ARM101，遥操作采集。划分 train 367、val 82、test 629。
  - 每条两路 1920×1080、30 fps 的 mp4；标注是一个 `annotations.json`，按示范给 `start_frame`、`end_frame`（左闭右开）和异常类型。异常 5 类：failed_grasp、collision、placement_failure、object_drop、object_not_dropped。
  - 有关节数据：`proprioception/<示范>.parquet`，列和 LeRobot 一样（`frame_index`、`timestamp`、`observation.state`、`action`），和视频逐帧对齐。所以关节体检也能在考卷 B 上考。
  - 评测协议：`evaluation/*.csv` 列出要评的帧；micro AUC 是所有被评的帧合起来算一个 AUC。四种设置 in_domain、cross_anomaly、cross_task、cross_task+anomaly；最难的那种最好成绩 67.4%。
  - 下载一个 `RoboVAD.zip`，6.86 GB。
  - **授权三处说法不一致**：zip 里的 `license.txt` 和 README 写 CC BY-NC-ND 4.0，Zenodo 元数据写 cc-by-4.0，arXiv 页面写 CC BY-SA 4.0（那应该是论文本身的授权）。按最严的 CC BY-NC-ND 处理：只拿来评测、报成绩，不改编、不再分发数据；商业用途要不要先问作者，由用户决定。

### 考卷 C：RoboMIND 失败示范（拿得到才做）

- 论文说有 5,000 条真实失败示范，每条都标了原因。Hugging Face 上的版本是 Apache-2.0 授权，要同意共享联系方式才能下载，总共 12.3 TB，目录里只看到 `success_episodes`。
- 2026-10-02 核：失败示范**已经公开**，在 Hugging Face 仓库的 `failure_data/` 目录，路径是 `<任务>/<失败原因>/<示范>/data/trajectory.hdf5`，95 个任务、1,678 条、440.9 GB，不是论文说的 5,000 条（另外的是否在 ModelScope 的 2.0 版里，未确认）。原因类别见第 5 节。成功示范按任务算，压缩后中位数 14 GB 一个任务，UR 机型中位数 1.4 GB，可以只挑小任务下。
- HDF5 结构：`master`（主臂）、`puppet`（从臂）、`observations/{rgb_images,depth_images}/<相机>`；Franka 和 UR 的 `joint_position` 8 维、最后一维是夹爪；AgileX 分 `_left`、`_right` 各 7 维；没有单独的 action，取 `master`；图像逐帧编码，Franka 和 UR 是 BGR。出处：官方仓库 `static/all_robot_h5_info.md`。帧率没写，拿到数据再核。
- 拿得到：报按示范的检出率，以及原因分类的准确率；只下一两个机型的几个任务。
- 拿不到：只用考卷 A 和 B，并在材料里说明。

## 9. 风险和对策

1. 不用训练的视频模型，在 RoboVAD 上可能不如论文里的方法。对策：和关节体检合起来用；成绩照实报，卖点放在「说得清原因」和「数据不出场」。
2. RoboMIND 的失败示范可能没公开。2026-10-02 核：公开了 1,678 条，这条风险基本解除；剩下的是体量（440.9 GB），只挑小任务下。
3. 已经有同类：数据厂商 Claru 自称逐条自动打分；开源的有 Loop-Engineering-for-VLA、hflow、kalanos。差异放在失败原因诊断、国内数采场三道质检的流程、数据不出场。
4. 没有客户试点，评委多半会问「哪个数采场在用」。下一步联系一家数采场试用，这是外部动作，由用户决定。
5. 赛事要求有完整合规的知识产权或授权证明。对策：代码自研；模型和数据附授权清单（Robometer、RoboMIND、考卷 A 的五个 SO-10x 数据集是 Apache-2.0，Cosmos 3 是 OpenMDW-1.1；RoboVAD 按最严的 CC BY-NC-ND 4.0 处理，见第 6 节）。

## 10. 开工第一天要核的

1. 海创π 参赛指南：初审交什么、什么时候交，复赛和决赛是线上还是线下。
2. RoboMIND：失败示范有没有公开、在哪里、原因怎么标。
3. RoboVAD：数据量、格式、有没有关节数据、评测协议。
4. Robometer-4B 用 BF16 要多少显存；社区 4 位量化版的授权和精度损失。
5. TOPReward 包的是哪个尺寸的 Qwen3-VL，要多少显存。
6. Cosmos 3 的授权，以及在 Nebius 上能不能直接调用；不能就在 Nebius AI Cloud 的 GPU 机器上自己跑。
7. 租 GPU 的价格。

每一条核完，结论写进本文对应的小节。

2026-10-02 核了第 2 到第 7 条（一个调研 agent，45 次工具调用，约 12.4 万 token）：

| 条目 | 结论 | 写在哪 |
|---|---|---|
| 1 参赛指南 | 没核，要加微信领 | 用户 |
| 2 RoboMIND | 失败示范公开了 1,678 条，原因 11 类 | 第 5 节、考卷 C |
| 3 RoboVAD | 6.86 GB，有关节数据；授权按 CC BY-NC-ND 处理 | 考卷 B |

## 12. 求职叙事

- 具身智能的数据工程：从数据格式、质检规则到评测基准，一条链做通。
